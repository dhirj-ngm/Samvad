**Version 2.1 - 24 October 2026. Local prototype implemented; human/device acceptance pending.**

The current observed setup and outstanding inputs are recorded in
[AI_DEMO_PREFLIGHT.md](AI_DEMO_PREFLIGHT.md). Stage new Sarvam preparation values
in ignored `api/.env.ai-demo-inputs` using the supplied preparation template;

[AI_DEMO_RUNBOOK.md](AI_DEMO_RUNBOOK.md) for operation and

## 1. Final decision and authority

Build a polished, bounded hackathon prototype that works through the presentation.
Preserve the full Android/iOS social UI/UX from P4.5: profiles, avatars, interests,
language settings, feed cards, likes, replies, follows, mentions, reposts and review.
Reduce the number of scenarios, not the product's visual appeal or interaction quality.

**Presentation baseline: four clearly labeled fictional demo personas having prepared
conversations, with actual persisted social interactions and optionally a small live
AI sequence.** Ten real testers remain optional additional evidence, not a blocker
or a claim that four seeded personas represent ten real participants.

Use hosted Qwen on Groq for text moderation and English summaries; use Sarvam
Translate for language conversion. Keep FastAPI between the phone and providers.
Do not train or self-host Gemma/Qwen, buy GPUs or build production infrastructure.
No model weights belong in the mobile app or gateway container.

This revision supersedes the previous ten-user-first AI handoff and the P4.5 AI
deferral for this newly requested AI implementation only. The social/profile work
must be preserved, including uncommitted changes. University-sized testing remains
pilot scale; Samvad is an India-first open conversation network, not a campus-only app.

This document authorizes the implementation scope for the subsequent implementation
thread. Updating this document does not deploy code, provision users, spend credits,
approve live publication, or claim provider/device testing passed.

- Current posts/replies persist as pending. Mobile calls screening after saving;

- Existing summaries are exactly three lines, news headline/excerpt only; translation
  uses Groq. App/database language checks currently support en/hi/ml.
- P4.5 may include uncommitted social/profile code, forward migrations and local

- Existing manual review can hide/restore reported content using a separate

- An `ai_pilot/` prototype, if present, is reference code only. Do not import blocking
  synchronous calls into async routes or bypass authentication/RLS/quotas/cache.

## 3. Demo modes and honest provenance

Keep content provenance independent from AI-result provenance. A fictional demo
account can request real live AI; a human-authored post can have cached AI output.

| Result | Meaning | Presentation |
|---|---|---|
| live | Successful actual provider call | Translated/generated by AI |
| cache | Previously successful provider output for the exact authorized source/version | Previously generated by AI |
| fixture | Human-authored or scripted output for an explicitly enabled predefined demo scenario | Demo example |
| original | Exact stored original; no translation needed | Original |

- Default to real valid cache for prepared scenarios. Prewarm using authorized live
  calls and human-review the results when credentials/credits are available.
- Fixture outputs are allowed only in explicit demo mode, for manifest-listed exact
  entity IDs and source hashes. Never use an unrelated preset for arbitrary new text.
  A cache miss must not silently become a fabricated live translation or moderation.
- Keep labels compact and polished: a demo-account note and accurate AI provenance,
  not debug screens or repeated infrastructure banners. Do not hide the distinction.
- Use the normal app screens/components and real persisted relationships. Do not
  replace working interactions with screenshots, hardcoded counts or disconnected UI.
- Cached results still require reachable app/backend/database infrastructure. This
  scope does not promise full offline Auth, feeds or private data synchronization.
- Keep `DEMO_MODE=false` by default. Fixture moderation is a scripted scenario only,
  never evidence that an arbitrary live post passed model review.

## 5. Bounded user-facing AI behavior

### Translation

- Pilot languages: English, Hindi and Malayalam only. Keep a central registry with
  app codes en/hi/ml and Sarvam codes en-IN/hi-IN/ml-IN. Native-script labels remain.
- Use `sarvam-translate:v1`, subject to verification against current account/docs.
  Published limit checked 24 October: 2,000 characters/request. Split longer input
  at sentence/paragraph boundaries with a Unicode-safe hard-split fallback; cap
  total work and validate every chunk. Preserve names, numbers, URLs and original text.
- Translate authorized visible post/reply IDs, never arbitrary inaccessible text
  supplied as proof of ownership. Same-language text requires no inference.
- Preserve `Translated by AI`, actual cache/fixture provenance and `Show original`.
  Provider failure leaves the original readable and offers a clear retry.
- Do not trust a user-declared language alone when evaluating mixed-language safety;
  include original text even when translation is uncertain. Unsupported/unreliable
  input remains pending for review, not automatically allowed.
- No new claim of full UI localization, language detection quality or 23-language
  support. More languages can follow after this demo.

### Moderation and server-owned submission

- Add an authenticated server submission path, preferably `/v1/submit-and-screen`,
  wrapping existing caller-authorized submit_post/submit_reply RPCs. Derive actor
  from verified identity; reuse original request UUID and reply parent/conversation.
- Persist pending content before provider calls. For non-English text Sarvam
  produces an English translation; Qwen receives BOTH original and translation as
  untrusted content, separate from the versioned system policy. No embedded user
  instruction can change the policy or claim administrator privileges.
- Permit ordinary satire/memes, criticism and civil disagreement. Hold clear
  high-severity threats, doxxing, sexual extortion and text apparently promoting
  non-consensual intimate material. Ambiguity requires review. No automated bans.
  This is text triage, not image analysis or legal certification.
- Use validated allow/review/hold outcomes mapped to allowed/flagged/blocked;
  only allowed becomes public. Failures stay pending, not mislabeled as blocked.
- A persisted save remains successful even if screening fails: return the saved
  entity/conversation ID, moderation_state, screening status and retryable flag.
  Define HTTP 200/202 and mobile handling before implementation. Never tell the
  user to create a new request UUID after an ambiguous save.
- For this bounded demo, await screening inside the request with bounded timeouts.
  If interrupted, provide author retry and a documented operator pending-recovery
  tool. Recovery uses the same saved ID and authorization; it cannot publish all
  pending records. Old direct RPC submissions remain pending until processed.
- Do not claim that every submission automatically completes after every disconnect.
  A production durable job/outbox worker is deferred unless demonstrated necessity
  makes it essential. Do not add Cloud Tasks/PubSub/microservices by default.
- Keep automatic live publication gated by documented human language/policy review.
  Prepared benign fixture content can be explicitly reviewed and seeded as approved,
  with provenance/audit; that does not approve unknown live content.
- Reuse atomic source-hash/state checks. Late AI results cannot undo a human
  decision, restore deleted text or remove P4.5 manual hiding.

### English/native summaries

- Add a compatible new `/v1/summarize` for news/post IDs. Keep the existing
  three-line `/v1/summarize-news` contract until its old callers are migrated.
- For adequate source material, return 4-5 concise English lines and, when
  requested/available, aligned Sarvam-translated native lines. Return explicit
  native-translation status so a translation failure does not discard good English.
- Include source basis, source URL for news, original target language, provider
  provenance and cache state. The UI offers English/native/full-original choices.
- News uses legitimately available headline/excerpt or already authorized source
  material. Keep `Headline-based brief` and return `insufficient_source` when there
  is too little information; never pad to five lines or invent unseen facts.
- Post summaries describe the author's argument, not invented thread consensus.
  Thread summaries, arbitrary URL fetching, scraping and full-article extraction
  are deferred. Existing 2,000-code-point post limits need not change for this demo.

## 6. Quotas, cache and latency

- Preserve Groq Free-plan/no-paid-fallback constraints. Add separate Sarvam
  character/request/credit accounting; its authorized cap defaults to zero until
  supplied. Never disable the global safety gate just to add a metered provider.
- Inspect current P4 limits (100 Groq requests/day, one concurrent call, bounded
  token/input budgets). Account for prompts plus original AND English translation.
  Existing conservative UTF-8-byte reservation can reject long Indic input; test
  maximum supported lengths and align config AND SQL ceilings deliberately.
  Do not raise limits above actual verified provider/account allowances.
- Prewarm only the fixture manifest's required translation pairs and summaries.
  Record actual calls/characters and stop at the permitted budget. A rehearsal
  should reuse cache rather than consume quota every time a card opens.
- Cache keys include task, entity ID/type, exact source hash, source/target language,
  provider/model IDs and policy/prompt/pipeline version. Post-summary and translation
  outputs must not collide when the same Qwen model is used for multiple tasks.
- Recheck original visibility/deletion/manual hiding on every cache retrieval and
  after slow calls. Protect pending/held text, fixture caches and private reports.
- Bound concurrency and retries, respect 429/Retry-After and do not rotate keys to
  evade limits. Keep original content usable when quota is exhausted.
- Measure the full Sarvam-plus-Qwen path; coordinate provider, server and mobile
  timeout budgets. Do not blindly increase only Cloud Run's request timeout while
  the mobile client still aborts at 30 seconds. Display saved/checking states cleanly.
